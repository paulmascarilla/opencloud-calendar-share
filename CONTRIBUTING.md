# Contributing

Thanks for your interest in opencloud-calendar-share. This guide explains how to propose a change and get it merged.

## Issue first

Every pull request must be linked to an issue that a maintainer has approved (label `approved`). Pull requests
without one are closed.

1. Search the [existing issues](https://github.com/paulmascarilla/opencloud-calendar-share/issues) first.
2. Open a **bug report** or a **feature request** from the templates.
3. Wait for a maintainer to approve it. For a feature, agree on the approach in the issue before you write code.

Discuss big changes before starting them: new features, API or Helm values changes, new dependencies (the sidecar
uses the Go standard library only), or changes to how calshare talks to Radicale and OpenCloud.

## Use of AI

- **Issues are written by a human.** Describe the problem, its context and what you expect in your own words. Do
  not paste text generated by an LLM.
- **Code and documentation may be written with AI tools**, but a human must review every line before the pull
  request is opened. You are responsible for the change: you understand it, you have tested it, and you can answer
  review comments about it.
- Say in the pull request which parts were written with AI.

## Getting started

1. Fork the repository on GitHub and clone your fork:
   ```sh
   git clone https://github.com/YOUR-USERNAME/opencloud-calendar-share.git
   cd opencloud-calendar-share
   git remote add upstream https://github.com/paulmascarilla/opencloud-calendar-share.git
   ```
2. Create a branch named after the issue:
   ```sh
   git checkout -b 42-short-description
   ```

[docs/development.md](docs/development.md) explains how to build the images, run them on kind and run the tests.

## Making changes

Run the checks for the components you touched. CI runs the same ones on every pull request and every push to
`main`: builds and tests in `.github/workflows/ci.yaml`, linters in `.github/workflows/lint.yaml`.

| Component | Checks |
|---|---|
| `sidecar/` (Go) | `gofmt -l .` prints nothing, `go vet ./...`, `go test -race ./...`, `golangci-lint run` (v2, config in `sidecar/.golangci.yaml`) |
| `web-extension/` (Vue, TypeScript) | `pnpm install --frozen-lockfile`, `pnpm lint` (ESLint), `pnpm check:types`, `pnpm build` |
| `charts/opencloud-calendar-share/` | `helm lint charts/opencloud-calendar-share --set opencloud.patch.enabled=true` |
| `deploy/compose/calendar.yml` | `docker compose config` on top of opencloud-compose (see the `compose` CI job) |
| YAML files | `yamllint .` (config in `.yamllint.yaml`; Helm templates are skipped) |
| Shell scripts | `shellcheck --severity=warning test/*.sh .github/scripts/*.sh` |

- Add or update tests for every behaviour you change. Sidecar changes need a Go test. Changes to invitations or
  sharing should also pass `test/e2e.sh` and `test/invitations-e2e.sh` against a live OpenCloud.
- UI changes: include a screenshot or a short recording in the pull request.
- Update the documentation in `docs/` and the README when you change user-facing behaviour, the REST API or Helm
  values.
- Never commit credentials (`tokens*.env` is ignored for this reason).

## Commit messages

We follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <description>`.

| Type | Use for |
|---|---|
| `feat` | a new feature |
| `fix` | a bug fix |
| `docs` | documentation only |
| `refactor` | a code change that neither fixes a bug nor adds a feature |
| `perf` | a performance improvement |
| `test` | adding or fixing tests |
| `build` | Dockerfiles, dependencies |
| `ci` | GitHub Actions workflows |
| `chore` | anything else that does not change the shipped code |

Scopes: `calshare`, `web`, `chart`, `compose`, `docs`. Mark breaking changes with `!` (`feat(chart)!: …`) and
explain them in the commit body.

```
fix(calshare): keep the organizer's time zone when a guest moves an event

Closes #42
```

CI checks the subject of every commit in a pull request, and the pull request title, which becomes the commit
subject when it is squashed. Subjects are 100 characters at most. Check your branch before pushing:

```sh
.github/scripts/commitlint.sh upstream/main..HEAD
```

## Pull requests

1. Rebase on the latest `main`:
   ```sh
   git fetch upstream
   git rebase upstream/main
   ```
2. Push your branch and open a pull request against `main`.
3. Fill in the template and link the approved issue (`Closes #42`).
4. Make sure CI is green.
5. Address review comments with new commits. A maintainer may squash them when merging.

## Releases

Only maintainers release, with the `tag` workflow: the version and [CHANGELOG.md](CHANGELOG.md) come from the
commit types, which is one more reason to write them carefully. See [Release](docs/development.md#release).

## Security

Do not report vulnerabilities in public issues. Use
[private vulnerability reporting](https://github.com/paulmascarilla/opencloud-calendar-share/security/advisories/new).
